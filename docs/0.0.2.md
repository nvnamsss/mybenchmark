## Phase 10 — AABB Scalar vs SIMD (game-server application)

Motivation: demonstrate SIMD applied to a real game-server workload — axis-aligned
bounding box (AABB) broadphase collision queries over 16 objects per pass.

### Struct designs

| Layout | File | Description |
|--------|------|-------------|
| `AABB` (Array of Structs) | `aabb_scalar_benchmark_test.go` | Natural Go layout; `Vec3{X,Y,Z}` nested |
| `AABB16` (Structure of Arrays) | `aabb_simd_benchmark_test.go` | 6× `[16]float32` fields; SIMD-friendly |

### Benchmarks

| Benchmark | Description | Scalar ns/op | SIMD ns/op | Speedup |
|-----------|-------------|-------------|-----------|--------|
| `*AABBIntersect16` | 16-box AABB vs query AABB — separating-axis | 32.16 | 3.453 | **9.3×** |
| `*AABBContainsPoint16` | 16-box point-in-AABB — separating-axis | 18.72 | 3.222 | **5.8×** |
| `*AABBExpand16` | 16-box grow by ±delta (pure arithmetic) | 42.66 | 6.652 | **6.4×** |

All 6 benchmarks: `0 B/op  0 allocs/op`.

### SIMD approach

Intersect16 and ContainsPoint16 use the *separating-axis gap* technique instead
of mask-AND chains (which trigger VPTERNLOGD spills on large stack frames):

```
gap = max(boxMin - queryMax, queryMin - boxMax)   // per axis (float32 arithmetic)
maxGap = max across X, Y, Z axes
intersects = maxGap.LessEqual(zero).ToBits()      // single mask op at end
```

Expand16 uses 6× BroadcastFloat32x16 + Sub/Add + Store — pure arithmetic,
no mask operations at all.

- [x] `aabb_scalar_benchmark_test.go` — `Vec3`, `AABB`, 3 scalar benchmarks, `b.Loop()`, 0 allocs
- [x] `aabb_simd_benchmark_test.go` — `AABB16` SoA, `//go:build goexperiment.simd`, 3 SIMD benchmarks, 0 allocs
- [x] All 6 benchmarks run cleanly; speedup ratios recorded above

## Phase 11 — Vec3 Scalar vs SIMD (Float32x4 per-vector design)

Motivation: benchmark the natural single-object SIMD Vec3 design — one `Float32x4`
register per vector (x=lane0, y=lane1, z=lane2, lane3=0 unused) — vs plain scalar `Vec3`.

### Struct designs

| Layout | Type | Description |
|--------|------|-------------|
| `Vec3` (scalar) | `struct{ X, Y, Z float32 }` | Existing; 3 separate float32 fields |
| `Vec3F4` (SIMD) | `struct{ v Float32x4 }` | x/y/z packed into 128-bit XMM register |

One `Float32x4` instruction replaces 3 sequential float32 ops, giving ~2–3× speedup.
Operations that require element shuffles (cross product) or horizontal reduction
(dot product) are excluded because `Float32x4.Permute` does not exist in archsimd.

### Benchmarks

| Benchmark | Description | Scalar ns/op | SIMD ns/op | Speedup |
|-----------|-------------|-------------|-----------|--------|
| `*Vec3Add16` | 16-pair element-wise add (VADDPS) | 19.26 | 12.30 | **1.6×** |
| `*Vec3Scale16` | 16-vec scale by 2.5 (VMULPS) | 16.51 | 10.31 | **1.6×** |
| `*Vec3Lerp16` | 16-pair lerp t=0.3 (VSUBPS + VFMADD213PS) | 35.24 | 14.78 | **2.4×** |

All 6 benchmarks: `0 B/op  0 allocs/op`.

Note: speedup is lower than SoA Vec3x16 (~9×) because each Float32x4 processes
one Vec3 (3/4 lanes used) while the loop still iterates 16 times. The advantage
is natural single-object abstraction — no batching required by the caller.

- [x] `vec3_scalar_benchmark_test.go` — reuses `Vec3`, 3 scalar benchmarks, 0 allocs
- [x] `vec3_simd_benchmark_test.go` — `Vec3F4`, `//go:build goexperiment.simd`, 3 SIMD benchmarks, 0 allocs
- [x] All 6 benchmarks run cleanly; speedup ratios recorded above

## Phase 12 — Resource-tick batch benchmark (game-server at 10,000 units)

Motivation: a game server runs a regen tick every frame for every unit — Hp, Mp, Sp.
The SIMD design packs 16 units into a single `Float32x16` batch (SoA layout) and
processes all 16 with one `Add + Min` pair per resource.

### Data layout

| Layout | File | Description |
|--------|------|-------------|
| Scalar SoA | `resource_scalar_benchmark_test.go` | 9 × `[10000]float32` package-level arrays |
| SIMD SoA | `resource_simd_benchmark_test.go` | 625 × `ResourceBatch` (9 `Float32x16` fields each) |

Total data size in both cases: 9 × 40,000 bytes = 360 KB (fits in L2 cache on Zen 4).

### Tick operation per unit

```
hp = min(hp + hpRegen, maxHp)
mp = min(mp + mpRegen, maxMp)
sp = min(sp + spRegen, maxSp)
```

Scalar: 30,000 iterations × 3 ops = 30,000 add+min pairs per tick.  
SIMD: 625 iterations × 3 `Float32x16.Add + Min` = ~3,750 SIMD instructions.

### Benchmarks

| Benchmark | Description | ns/op | Speedup |
|-----------|-------------|-------|---------|
| `BenchmarkScalarResourceTick` | 10,000-unit for-loop tick | 27,162 | baseline |
| `BenchmarkSIMDResourceTick` | 625 × `ResourceBatch.Tick()` | 3,065 | **8.9×** |

Both benchmarks: `0 B/op  0 allocs/op`.  
CPU: AMD Ryzen 9 7940HS (Zen 4, AVX512).

- [x] `resource_scalar_benchmark_test.go` — 9 arrays, `init()`, `BenchmarkScalarResourceTick`, 0 allocs
- [x] `resource_simd_benchmark_test.go` — `ResourceBatch`, 625 batches, `//go:build goexperiment.simd`, 0 allocs
- [x] Both benchmarks run cleanly; 8.9× speedup recorded above
