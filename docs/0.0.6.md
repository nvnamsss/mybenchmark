# 0.0.6 — Benchmark: Multithreaded Synchronization Approaches

Compare the performance hierarchy of synchronization primitives described in
*The Art of Multiprocessor Programming* (Herlihy & Shavit) using real Go benchmarks.
Each approach protects the same shared counter increment to isolate synchronization cost.

## Phase 1 — Coarse-Grained Locking (Slowest)

Single global mutex protecting all shared state. Every goroutine competes for the same lock.

**File:** `coarse_grained_benchmark_test.go`

- [x] `BenchmarkScalarCoarseGrainedCounter` — baseline single-threaded, no contention
- [x] `BenchmarkCoarseGrainedCounter_2G` — 2 goroutines, one shared `sync.Mutex`
- [x] `BenchmarkCoarseGrainedCounter_4G` — 4 goroutines, one shared `sync.Mutex`
- [x] `BenchmarkCoarseGrainedCounter_8G` — 8 goroutines, one shared `sync.Mutex`
- [x] `BenchmarkCoarseGrainedCounter_16G` — 16 goroutines, one shared `sync.Mutex`

**Status:** ✅ COMPLETE

**Results (10-run medians):**
- 1G: 4.45 ns/op (uncontended)
- 2G: 5.93 ns/op (1.33x)
- 4G: 9.75 ns/op (2.19x)
- 8G: 19.38 ns/op (4.35x)
- 16G: 22.50 ns/op (5.06x)

**Analysis:** Linear scaling degradation with contention. Each goroutine must wait for the global lock.

## Phase 2 — Fine-Grained Locking

Partition shared state into N shards, each with its own lock. Goroutines only contend
within the same shard.

**File:** `fine_grained_benchmark_test.go`

- [x] `BenchmarkScalarFineGrainedCounter` — baseline single-threaded
- [x] `BenchmarkFineGrainedCounter_2G` — 2 goroutines, 2 shards (1 lock each)
- [x] `BenchmarkFineGrainedCounter_4G` — 4 goroutines, 4 shards
- [x] `BenchmarkFineGrainedCounter_8G` — 8 goroutines, 8 shards
- [x] `BenchmarkFineGrainedCounter_16G` — 16 goroutines, 16 shards

**Status:** ✅ COMPLETE

**Results (10-run medians):**
- 1G: 4.99 ns/op
- 2G: 8.32 ns/op (1.67x)
- 4G: 13.31 ns/op (2.67x)
- 8G: 23.22 ns/op (4.65x)
- 16G: 10.79 ns/op (2.16x - **perfect partitioning reduces contention**)

**Analysis:** Better scaling than coarse-grained. At 16G with 16 shards, each goroutine gets its own lock—minimal contention, 2.1x faster than coarse-grained at same scale.

## Phase 3 — Optimistic Synchronization (STM-style)

Read without locking, validate, retry on conflict. Uses atomic CAS in a retry loop to detect races.

**File:** `optimistic_benchmark_test.go`

- [x] `BenchmarkScalarOptimisticCounter` — baseline single-threaded
- [x] `BenchmarkOptimisticCounter_2G` — 2 goroutines, CAS retry loop
- [x] `BenchmarkOptimisticCounter_4G` — 4 goroutines
- [x] `BenchmarkOptimisticCounter_8G` — 8 goroutines
- [x] `BenchmarkOptimisticCounter_16G` — 16 goroutines

**Status:** ✅ COMPLETE

**Results (10-run medians):**
- 1G: 3.15 ns/op (fastest uncontended - just CAS)
- 2G: 6.80 ns/op (2.16x)
- 4G: 11.25 ns/op (3.57x)
- 8G: 15.45 ns/op (4.90x)
- 16G: 16.39 ns/op (5.20x - retries plateau benefit)

**Analysis:** Fast under low contention, but retry overhead accumulates. Worse than lock-free at high contention.

## Phase 4 — Lock-Free (Atomic CAS)

Use `sync/atomic` primitives directly. No mutex, no OS scheduler involvement.

**File:** `lock_free_benchmark_test.go`

- [x] `BenchmarkScalarLockFreeCounter` — baseline single-threaded `atomic.AddInt64`
- [x] `BenchmarkLockFreeCounter_2G` — 2 goroutines, `atomic.AddInt64`
- [x] `BenchmarkLockFreeCounter_4G` — 4 goroutines
- [x] `BenchmarkLockFreeCounter_8G` — 8 goroutines
- [x] `BenchmarkLockFreeCounter_16G` — 16 goroutines

**Status:** ✅ COMPLETE

**Results (10-run medians):**
- 1G: 2.87 ns/op (lowest baseline - hardware primitive)
- 2G: 3.99 ns/op (1.39x)
- 4G: 5.68 ns/op (1.98x)
- 8G: 7.05 ns/op (2.46x)
- 16G: 7.59 ns/op (2.65x - **excellent horizontal scaling**)

**Analysis:** Lock-free outperforms all mutex-based approaches under contention. Only 2.65x slowdown at 16G vs 5.06x for coarse-grained.

## Phase 5 — Thread-Local Reduction (Best Pattern)

Each goroutine increments its own private counter. At the end, results are combined once.
This is the "no shared state during hot path" pattern—zero contention during computation.

**File:** `thread_local_benchmark_test.go`

- [x] `BenchmarkScalarThreadLocalCounter` — baseline single-threaded
- [x] `BenchmarkThreadLocalCounter_2G` — 2 goroutines, private counters + final merge
- [x] `BenchmarkThreadLocalCounter_4G` — 4 goroutines
- [x] `BenchmarkThreadLocalCounter_8G` — 8 goroutines
- [x] `BenchmarkThreadLocalCounter_16G` — 16 goroutines

**Status:** ✅ COMPLETE

**Results (10-run medians):**
- 1G: 0.76 ns/op (bare increment)
- 2G: 0.38 ns/op (0.50x - **faster with more threads!**)
- 4G: 0.13 ns/op (0.17x)
- 8G: 0.12 ns/op (0.16x)
- 16G: 0.08 ns/op (0.11x - **near-zero overhead**)

**Analysis:** Scales inversely (gets faster with parallelism) because each goroutine operates independently. No synchronization cost in hot path. **Speedup vs coarse-grained at 16G: 281x**

## Phase 6 — RWMutex (Read-Heavy Workload)

Separate read and write locking. Multiple readers can proceed concurrently; writers are exclusive.

**File:** `rwmutex_benchmark_test.go`

- [x] `BenchmarkScalarRWMutexRead` — baseline single-threaded read
- [x] `BenchmarkRWMutexRead_8G` — 8 readers, 0 writers (pure read throughput)
- [x] `BenchmarkRWMutexReadWrite_8G_1W` — 8 goroutines: 7 readers + 1 writer
- [x] `BenchmarkRWMutexReadWrite_8G_4W` — 8 goroutines: 4 readers + 4 writers
- [x] `BenchmarkMutexReadHeavy_8G` + `BenchmarkRWMutexReadHeavy_8G` — `sync.Mutex` vs `sync.RWMutex` at 87.5% read

**Status:** ✅ COMPLETE

**Results (10-run medians):**
- Scalar baseline: 4.02 ns/op (single-threaded RLock)
- RWMutex pure read (8G): **14.47 ns/op** ✅ RWMutex advantage (concurrent readers)
- RWMutex 7R+1W (8G): 35.57 ns/op ⚠️ Writer blocks readers
- RWMutex 4R+4W (8G): 25.42 ns/op (more balanced contention)
- Mutex baseline 7R+1W (8G): **15.92 ns/op** (simpler, better for mixed)
- RWMutex 7R+1W (8G): 34.09 ns/op **2.14x slower than Mutex**

**Key Finding:** RWMutex is **not universally superior**:
- ✅ Excels at pure reads (14.47 ns/op, concurrent readers proceed)
- ❌ Worse than Mutex on mixed workloads (34.09 vs 15.92 ns/op) due to lock management overhead
- Analysis: See `PHASE_6_RESULTS.md` for detailed coefficient of variation and scaling analysis

**Status:** ✅ COMPLETE - Comprehensive results with 250+ benchmark runs, full statistical analysis

**Key Findings:**
- **Thread-local reduction is 482x faster** than coarse-grained at 16G (0.049 ns/op vs 23.64 ns/op)
- **Lock-free atomic is universally best** general-purpose synchronization (3.05x speedup at 16G)
- **Fine-grained locking is risky** — worse than coarse-grained at 4G (0.37x) but better at 16G (1.78x)
- **Optimistic CAS has limited benefit** (1.05x at 16G), high variance, retry overhead dominates
- **RWMutex paradox:** Slower than Mutex on mixed workloads (2.14x) despite being "more advanced"

See [PHASE_8_RESULTS.md](PHASE_8_RESULTS.md) for detailed analysis, scaling efficiency breakdown, and performance hierarchy validation against Herlihy & Shavit.

| Rank | Approach               | @ 16G         | Speedup     | Best For                                 |

### Key Insights

- **Lock-free atomic is safest general-purpose choice** (3.05x speedup consistently)
- **Thread-local reduction is transformative** when applicable (482x speedup)
- **Fine-grained locking is risky** (0.37x at 4G, needs careful design)
- **RWMutex paradox:** 2.14x SLOWER than Mutex on mixed workloads
- **Performance hierarchy is context-dependent**, not fixed
