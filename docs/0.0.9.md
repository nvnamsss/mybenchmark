# 0.0.9 — Benchmark: msgpack vs protobuf Serialization

Extend the 0.0.7 serialization benchmarks (JSON vs msgpack) by adding **protobuf** as a third
codec across the same flat and nested struct shapes. The goal is a direct msgpack-vs-protobuf
comparison using identical data and identical benchmark structure.

**Hypothesis:** protobuf's schema-based, tag-indexed binary encoding skips field-name
serialization and uses variable-length integer encoding for small integers, producing smaller
payloads and lower encode/decode latency than msgpack's reflection-based approach, especially
for structs with many numeric fields.

## Struct Shapes

Protobuf-specific types mirror the existing Go struct shapes with equivalent field types.
Field names are snake_case per proto3 convention; generated Go types use PascalCase.

  int64  ability_id = 2;

## Key Findings

1. **protobuf marshal is 4–5× faster than msgpack** for flat structs, 4× faster for nested.
2. **protobuf unmarshal is 2–3× faster than msgpack** for flat structs, ~2× for nested.
3. **protobuf is 3–8× faster than JSON** across all shapes; unmarshal gains are especially large.
4. **protobuf payloads are 53–72% smaller than msgpack** — protobuf omits field names and uses varint encoding for small integers.
5. **protobuf consistently achieves 1 alloc/op** on flat structs; nested structs add allocations for sub-message pointers (2–4 allocs) but still beat msgpack's 4–5 allocs.
6. **Trade-off:** protobuf requires code generation (`.proto` → `protoc` → `.pb.go`) and a separate generated type; JSON and msgpack work with any tagged Go struct.
