# 0.0.4 — Benchmark: Redis-based Rate Limiter (real network)

Replace the in-process channel store with a real Redis client to produce honest
throughput numbers. Measure the actual per-request latency of the exact (one INCR
per call) and approximate (batched INCRBY) designs, and quantify the accuracy
trade-off (over-admission) of the approximate approach.

---

## Prerequisites

- [x] Confirm Redis is installed and reachable on `localhost:6379`
- [x] Add Redis client dependency: `go get github.com/redis/go-redis/v9`
- [x] Confirm `go.mod` reflects the new dependency after `go mod tidy`

---

## Phase 1 — Redis-backed store (`rate_limiter_redis_benchmark_test.go`)

- [x] Implement `redisStore` wrapping `redis.Client` with the same interface as `centralStore`:
  - `add(key string, delta int64) bool` — issues `INCRBY key delta` then checks against the limit; sets `EXPIRE` on first write (key TTL = window duration)
  - `close()` — closes the Redis client connection
- [x] Implement `RedisExactRateLimiter` — calls `redisStore.add(key, 1)` on every `Allow()` (one network RTT per request; naive baseline)
- [x] Implement `RedisApproxRateLimiter` — accumulates increments in a local `atomic.Int64`; flushes to Redis with a single `INCRBY` every `batchSize` (100) calls
- [x] Add skip guard: if `redis.NewClient(...).Ping(ctx)` fails, call `b.Skip("Redis not available")` so CI without Redis does not break

---

## Phase 2 — Throughput benchmarks

- [x] `BenchmarkRedisExact_Allow` — single goroutine, healthy key, one INCR per call; establishes the real-network baseline
- [x] `BenchmarkRedisApprox_Allow` — single goroutine, same key, batched INCRBY; measures admission-check overhead with real Redis flushes
- [x] `BenchmarkRedisApprox_Allow_Parallel` — `b.RunParallel` version; reports `req/s` via `b.ReportMetric`
- [x] Record speedup ratio (Exact ns/op ÷ Approx ns/op) — **~93×** (552,000 ns ÷ 5,960 ns)

---

## Phase 3 — Accuracy measurement

- [x] `TestRedisApprox_OverAdmission` — sends exactly `limit + batchSize` requests to a fresh key and counts how many were admitted above the limit; assert over-admission ≤ `batchSize - 1` (worst-case one incomplete batch)
- [x] Flush the test key with `DEL` in `t.Cleanup` so the test is idempotent
- [x] Document the accuracy trade-off: measured **18.8% over-admission** on 20 nodes (limit=10,000, thresh=100); theoretical worst case is `numNodes × thresh / limit = 20%`; hop reduction **168×** (119 Redis calls vs 20,000 exact)
