# 0.0.10 — Timer Benchmark: Busy-wait vs timerfd vs PREEMPT_RT

Design and benchmark three approaches to reduce timer jitter in a 30 Hz game loop:
1. **Busy-wait**: sleep ~33ms - 500µs, then spin until exact target time
2. **timerfd**: Linux kernel `CLOCK_MONOTONIC` + `epoll_wait`
3. **PREEMPT_RT**: Real-time kernel with `SCHED_FIFO` priority

Measure CPU cost, memory cost, and jitter (both per-tick latency and statistical aggregate).

---

## Requirements

- **Target**: 30 Hz (33.333 ms interval)
- **Platforms**: Linux only (all three approaches)
- **Test duration**: ~10 seconds per benchmark (300 ticks at 30 Hz)
- **Jitter measurement**:
  - Per-tick: record actual fire time delta from target (microsecond precision)
  - Statistical: min, max, p50, p99, stddev from all ticks
- **Load scenarios**:
  - **Idle load**: timer alone, no background work
  - **Active load**: 8 background goroutines busy-spinning (simulating game logic)

### Phase 2: Implement busy-wait backend

**File**: `timer_busywait_benchmark_test.go`

- [ ] Implement `BusyWaitBackend` struct:
  ```go
  type BusyWaitBackend struct {
      interval time.Duration        // 33.333 ms
      tickCh   chan time.Time        // buffered, capacity=1
      stopCh   chan struct{}
      spinDur  time.Duration         // 500 µs
  }
  ```

- [ ] Implement `Start()`:
  ```
  next := now.Add(interval)
  for {
      sleepFor := time.Until(next) - spinDur
      if sleepFor > 0 {
          time.Sleep(sleepFor)
      }
      for time.Now().Before(next) {
          runtime.Gosched()  // yield, don't fully spin
      }
      tickCh <- time.Now()
      next = next.Add(interval)
  }
  ```

- [ ] Write `BenchmarkBusyWaitBackend_Idle`
- [ ] Write `BenchmarkBusyWaitBackend_ActiveLoad`

**Expected results**:
- CPU: ~15–20 ms per 10 seconds (500µs spinning × 300 ticks ≈ 150ms raw spin time, runtime.Gosched() yields most of it)
- Memory: ~0 B/op, ~0 allocs/op
- Jitter: ~50–100 µs p99 (spin loop removes OS scheduling variance)

### Phase 5: Benchmark harness and jitter collection

**File**: `timer_harness.go` (utility package)

- [ ] Implement `runTimerBenchmark()`:
  ```go
  func runTimerBenchmark(b *testing.B, backend TimerBackend, targetHz int, withLoad bool) *Stats {
      backend.Start()
      defer backend.Stop()
      
      // Optional: start load goroutines
      if withLoad {
          startLoadGoroutines(8)
      }
      
      // Record per-tick deltas
      targetInterval := time.Duration(1000*1000*1000 / targetHz) * time.Nanosecond
      deltas := make([]int64, 0)
      startTime := time.Now()
      targetTime := startTime
      
      for tick := range backend.Ticks() {
          now := time.Now()
          delta := (now.Sub(targetTime) - targetInterval).Microseconds()
          deltas = append(deltas, delta)
          targetTime = targetTime.Add(targetInterval)
          
          if now.Sub(startTime) >= 10*time.Second {
              backend.Stop()
              break
          }
      }
      
      return computeStats(backend.Name, deltas)
  }
  ```

- [ ] Implement `computeStats()`:
  - Read performance counters (CPU time, allocations via `b.AllocatedBytes()`, etc.)
  - Sort deltas for percentile computation

## Summary and Recommendations

### Trade-offs

| Approach | Jitter P99 | CPU Cost (10s) | Memory | Complexity | Platform | Notes |
|----------|-----------|------------|--------|-----------|----------|-------|
| Ticker | pending | pending | 0 | minimal | all | Go runtime timer; baseline |
| BusyWait | pending | pending | 0 | low | all | Spin loop; ~1% CPU overhead |
| timerfd | pending | pending | 0 | medium | Linux | Kernel timer; deterministic |
| PREEMPT_RT | pending | pending | 0 | medium | Linux* | RT kernel required; best latency |

**Legend**: 
- Jitter P99 in microseconds (lower is better)
- CPU Cost is total milliseconds used per 10-second run
- `*` PREEMPT_RT requires kernel patch + `CAP_SYS_NICE`; gracefully degrades to timerfd

### Recommendations

#### For Game Servers (production)

**Use Busy-wait (Approach 1)** if:
- Current 1ms jitter is acceptable for hit registration and movement smoothness
- You want minimal complexity and cross-platform support
- 1% CPU overhead on one core is negligible (16-core machines)
- Game can tolerate 50–100 µs variance

#### For Deterministic Workloads

**Use timerfd (Approach 2)** if:
- Linux-only deployment is acceptable
- Sub-millisecond jitter is required but 100–200 µs is tolerable
- You want zero extra CPU spinning
- Standard kernel (no custom build)

#### For Real-time Guarantees

**Use PREEMPT_RT (Approach 3)** if:
- 10–50 µs jitter is required (trading latency for cost)
- Real-time kernel is available (custom build)
- Process has `CAP_SYS_NICE` capability
- Can afford kernel maintenance burden
- Production environment (e.g., high-frequency trading, autonomous vehicles)

## Notes

- Keep `stopCh` in all backends for clean shutdown
- Use `testing.B.ReportMetric()` to report custom metrics (jitter min/max/p99)
- Beware: PREEMPT_RT requires kernel patch + CAP_SYS_NICE; gracefully degrade to standard timerfd if unavailable
- Busy-wait with `runtime.Gosched()` prevents CPU monopolization but still yields time to other goroutines
- Run benchmarks with `-bench=. -benchmem -count=3` to get stable results
- All jitter measurements in microseconds (µs) for precision; 1 ms = 1000 µs
